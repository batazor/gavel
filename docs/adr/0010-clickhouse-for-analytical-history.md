# 10. Postgres for operational state, ClickHouse for analytical history

Date: 2026-10-21

## Status

Accepted

## Context

«История торгов» — это два разных профиля нагрузки:

1. **Операционная**: последние изменения цены по лоту, дозапрос после переподключения SSE (ADR-0006, ADR-0008). Точечные чтения по ключу, низкая задержка, высокая конкурентность.
2. **Аналитическая**: графики цены, динамика по категориям, средняя цена закрытия, активность по часам, аудит за длинный период. Агрегации по миллионам событий.

Рассматривали Cassandra и ClickHouse как второе хранилище. Cassandra не агрегирует, требует LWT для условных записей и тяжела в kind. ClickHouse — колоночный, со встроенными движками Kafka и NATS, одним бинарником и родным datasource в Grafana.

## Decision

- **Postgres** остаётся хранилищем по умолчанию: event store, outbox и операционные проекции каждого контекста (ADR-0004, ADR-0005).
- **ClickHouse** — отдельный bounded context **Analytics**. Хранит только неизменяемые публичные события (`PriceChanged`, `AuctionOpened`, `AuctionClosed`, `LotListed`), читает их **напрямую из брокера** движком Kafka или NATS в MaterializedView. Отдельного consumer-сервиса нет.
- Потребители аналитики: **Grafana** (дашборды торгов в том же стеке, что телеметрия) и **BFF** для графика цены на странице лота. Горячий путь ставки от ClickHouse не зависит.
- Cassandra из кандидатов убрана.

## Consequences

- Выбор брокера (отдельный ADR) ограничен тем, что умеет читать ClickHouse: Kafka-совместимые (Kafka, Redpanda) или NATS JetStream.
- ClickHouse — eventually consistent проекция. График может отставать на секунды, для страницы лота это приемлемо, для цены — нет, цена идёт через SSE.
- Приватные события (`MaxBidPlaced`) в ClickHouse не попадают: туда идёт только то, что уже вышло через outbox как публичное.
- В kind добавляется ещё один pod. Приемлемо, ClickHouse стартует с сотнями мегабайт.
- На перспективу PostHog живёт на ClickHouse, продуктовую аналитику можно будет положить рядом.
