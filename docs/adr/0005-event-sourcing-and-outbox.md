# 5. Event sourcing for Auction, transactional outbox for integration

Date: 2026-10-21

## Status

Accepted

## Context

Ставки — естественный поток событий. Нужен полный аудит торгов (кто, когда, сколько), воспроизводимость спорных ситуаций и материал для Lean: инварианты формулируются над последовательностью событий проще, чем над мутируемым состоянием. Сервисы разделены по контекстам (ADR-0004), и между ними нужна надёжная доставка событий без распределённых транзакций.

## Decision

1. **Event sourcing в контексте Auction.** Агрегат Auction — свёртка событий `AuctionOpened`, `BidPlaced`, `AuctionClosed`, `WinnerDetermined`. Состояние не хранится, хранится append-only журнал в `auction-db`. Read-модели (текущая цена, история ставок) — проекции.
2. **Transactional outbox** для публикации наружу. Событие и строка outbox пишутся в одной транзакции с журналом. Отдельный relay читает outbox и публикует в брокер. Для Catalog outbox работает поверх обычного CRUD-состояния, event sourcing там не нужен.
3. **Брокер** нужен, но конкретный (NATS JetStream, Kafka, Redpanda) выбирается отдельным ADR после оценки нагрузки и удобства в kind.

## Consequences

- Lean доказывает свойства функции `apply : State → Event → State` и команд, которые порождают события. Это прямое соответствие коду.
- Оптимистическая конкуренция через версию потока: две ставки в одну миллисекунду дают конфликт версии, одна проигрывает и повторяется. Это решает вопрос конкурентных ставок явно.
- Схема событий становится публичным контрактом, её нужно версионировать.
- Snapshots пока не делаем: аукцион живёт часы или дни, событий на поток немного.
- Keploy записывает HTTP, но не журнал событий. Тесты агрегата — чистые unit и property-based тесты поверх списка событий.
