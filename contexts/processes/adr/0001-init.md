# 1. Инициализация Processes

Date: 2026-10-21

## Status

Accepted

## Что

Processes — Rust process worker для сквозных процессов на Temporal. Он реализует durable-таймеры, саги и повторяемые activities, которые координируют bounded contexts через их публичные команды и события.

## Зачем

Закрытие торгов по времени, снятие лота с компенсацией и ожидание оплаты переживают рестарты и охватывают несколько владельцев данных. Эти намерения во времени нельзя надёжно реализовать ни в HTTP-запросе, ни внутри одного bounded context.

Рассматривались три роли Temporal: только таймер закрытия, слой всех сквозных процессов и хост доменного агрегата. Выбран слой процессов. Entity workflow отвергнут: история Temporal стала бы вторым журналом событий, домен зависел бы от SDK, а брокер и outbox всё равно остались бы для остальных подписчиков.

## Требования

- Использовать Temporal для намерений во времени, а Redpanda — для фактов и pub/sub.
- Реализовать `AuctionLifecycle`, `WithdrawLot` и `SettleAuction` как workflow process worker.
- В `SettleAuction` последовательно обрабатывать settlement candidates: уведомление, автоматическая попытка через provider-neutral Payments, двухчасовой recovery timer, forfeiture, следующий кандидат.
- Считать двухчасовое окно, порядок кандидатов и момент перехода бизнес-политикой процесса, а не возможностями конкретного платёжного провайдера.
- Общаться с Payments только его нейтральными командами и событиями; workflow не знает API-объектов и статусов Stripe или другого провайдера.
- Отправлять уведомления через provider-neutral Notify; workflow выбирает момент и template key, но не владеет каналом, шаблоном и delivery retry.
- Не хранить в workflow состояние торгов и не дублировать доменные решения.
- Получать факты из брокера, запускать workflow или отправлять им сигналы.
- Вызывать только идемпотентные activities с безопасными повторами.
- Генерировать gRPC clients из versioned modules владельцев Auction, Catalog, Payments и Notify; задавать deadline и повторять только retryable transport failures с тем же idempotency key.
- Передавать время в доменные команды явно.
- Обрабатывать отказы доменных команд как ожидаемый результат процесса.
- Изолировать Temporal server и его Postgres от баз bounded contexts.
- Использовать проверенную workload identity `service_account:processes`; не выполнять системные команды с пользовательским principal и проходить SpiceDB permissions `execute_withdraw`, `close`, `cancel`, `reopen`, `settle`, `process`, `send_notifications`.
- Владеть узким Federation adapter для старта process commands и чтения `Operation`; Cosmo Router не использует Temporal client напрямую.
- Публиковать Temporal SDK metrics и process-level SLI согласно локальному [observability ADR](0002-workflow-observability.md); нормальное ожидание durable timer не считать зависанием.

- Поставлять собираемый bootstrap binary и собственные multi-stage Dockerfile, Helm chart, ServiceMonitor, PrometheusRule, Grafana dashboard в `ops/`; platform chart не хранит project-specific manifests.

## Последствия

- Durable-таймеры, повторы и компенсации переживают рестарты worker.
- Temporal не заменяет брокер и не становится single writer доменного потока.
- В kind добавляются process worker, Temporal server и его Postgres.
- Restate остаётся запасным вариантом, если эксплуатационный вес Temporal окажется неприемлемым.
- Workflow не рассчитывает следующего кандидата и цену: это команда в Auction и решение его агрегата.
