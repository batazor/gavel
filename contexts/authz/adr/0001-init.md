# 1. Инициализация Authz

Date: 2026-10-22

## Status

Accepted

## Что

Authz — отдельный Rust project с policy API поверх SpiceDB. Он владеет authorization schema и relationship graph для Gavel resources. JWT от внешнего OAuth/OIDC provider остаётся источником аутентифицированной личности, но роли и resource permissions из JWT не принимаются.

## Зачем

Права уже пересекают несколько владельцев: продавец редактирует и снимает лот, участник видит своё состояние и продолжает только свою оплату, process worker закрывает аукцион и запускает списание. Проверки по локальным `seller_id`/`user_id` быстро расходятся между BFF и сервисами и не дают единой модели делегирования, аудита и последующего добавления moderator/admin access.

Рассмотрены локальные RBAC-проверки, JWT roles и relationship-based authorization. Выбран SpiceDB: права выражаются через relations и вычисляемые permissions, а OAuth-токен не становится долгоживущим снимком доступа.

## Требования

- Канонический user principal выводить из verified `(iss, sub)` как неперсональный base64url/hash id; email не использовать как id.
- После первого verified login идемпотентно регистрировать principal как `platform:member`; удаление membership немедленно запрещает authenticated capabilities без собственной user profile DB.
- Представлять process worker отдельным `service_account`, полученным из проверенной workload identity/mTLS, а не из пользовательского header.
- Сервис-владелец выводит end-user principal из JWT, повторно проверенного на своей mesh-boundary, либо из подписанного token-exchange assertion. Не доверять произвольным `X-User-Id`/`X-Principal` от вызывающего сервиса.
- Использовать схему [`schema/gavel.zed`](../schema/gavel.zed) как source of truth и проверять assertions из [`gavel.validation.yaml`](../schema/gavel.validation.yaml) в CI.
- Писать relationships через Authz relationship writer. Он авторизует caller по mTLS workload identity и разрешает каждому контексту только его resource types; raw SpiceDB write API и admin token прикладным сервисам недоступны.
- Проверять permission в сервисе-владельце команды. Edge/subgraph pre-check нужен для UX, но не является единственной защитой.
- Не переносить в SpiceDB изменчивые бизнес-инварианты: состояние аукциона, размер ставки, payment readiness, settlement order и deadline остаются в доменах.
- Для создания заранее выделять resource id и идемпотентно записывать обязательные grant relationships, затем одной локальной транзакцией сохранять ресурс, ZedToken и outbox. Так Debezium не опубликует ресурс раньше прав; failed local commit оставляет только безвредный orphan tuple для reconciliation.
- Derived grant, известный только после принятой команды (`auction:participant`), записывать после domain commit, но не считать command provisioning завершённым до успешного tuple write. До retry/reconciliation private read fail closed; публичное событие identity не раскрывает.
- Revocation выполнять в SpiceDB до доменной публикации и сохранять returned ZedToken. Read-after-write/revocation checks используют `at_least_as_fresh`; security-sensitive проверки после отзыва могут использовать `fully_consistent`.
- Mutations и private reads fail closed при timeout/error SpiceDB. Public reads не зависят от Authz.
- Authz service и SpiceDB запускаются минимум в трёх replicas с отдельным HA Postgres datastore; raw SpiceDB API доступен только Authz service и schema migration job.
- Permission names являются межпроектным контрактом и меняются backward-compatible migration: expand → migrate tuples/callers → contract.
- Не публиковать permission и relationship APIs через Federation; они остаются внутренним interface, недоступным браузеру.
- Владеть versioned gRPC contract `CheckPermission`, `BulkCheckPermissions`, `RegisterPrincipal`, `WriteRelationships`; caller scope выводить из mTLS workload identity.
- Перед внешним mutation атомарно claim-ить `(caller, idempotency_key)` в отдельном Authz PostgreSQL receipt store. Exact replay возвращает durable result, иной canonical payload конфликтует, а истёкший lease разрешает безопасно повторить тот же идемпотентный TOUCH/delete.
- Хранить Authz receipts отдельно от SpiceDB datastore: SQL migration job изменяет только receipt schema, а независимый schema job применяет `.zed` contract.

- Поставлять собираемый bootstrap binary и собственные multi-stage Dockerfile, Helm chart, ServiceMonitor, PrometheusRule, Grafana dashboard в `ops/`; platform chart не хранит project-specific manifests.

## Последствия

- Аутентификация, authorization и domain eligibility становятся тремя явными этапами.
- Relationship graph дублирует только access-relevant edges, а не доменное состояние целиком.
- Появляется synchronous dependency на SpiceDB в private/mutation paths и на PostgreSQL receipt store в mutation paths; BulkCheck и connection pooling проверяются нагрузочными тестами.
- ZedTokens защищают causal consistency и от stale allow после изменения отношений.
