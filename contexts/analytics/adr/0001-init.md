# 1. Инициализация Analytics

Date: 2026-10-21

## Status

Accepted

## Что

Analytics — проект аналитической истории торгов на ClickHouse. Он строит долгоживущие проекции публичных событий и предоставляет данные Grafana и read-only Federation subgraph. Postgres остаётся хранилищем операционного состояния проектов; ClickHouse не заменяет его и не участвует в командах.

## Зачем

«История торгов» содержит два разных профиля нагрузки:

1. **Операционный:** последние изменения цены по лоту и replay после переподключения GraphQL subscription. Это точечные чтения по ключу с низкой задержкой и высокой конкурентностью; их обслуживают операционные проекции в Postgres.
2. **Аналитический:** графики цены, динамика по категориям, средняя цена закрытия, активность по часам и аудит за длинный период. Здесь нужны агрегации по миллионам событий.

Рассмотрены Cassandra и ClickHouse. Cassandra не предназначена для аналитических агрегаций, требует LWT для условных записей и тяжела для локального kind-кластера. ClickHouse — колоночное хранилище со встроенным Kafka engine и готовым datasource для Grafana. Поэтому аналитический профиль выделен в отдельный проект Analytics на ClickHouse.

## Требования

- Использовать Postgres для event store, outbox и операционных проекций проектов.
- Использовать ClickHouse только для аналитической истории и агрегатов.
- Принимать только публичные события из топиков владельцев контекстов; приватные максимумы ставок не покидают Auction.
- Хранить неизменяемые `PriceChanged`, `BidRecorded`, `AuctionOpened`, `AuctionClosed`, `LotListed` и другие публичные события.
- Предоставлять через Analytics subgraph полную курсорную историю принятых ставок по лоту. Запись содержит публичный alias и результирующую цену, но никогда не `user_id` или секретный максимум.
- Дедуплицировать at-least-once delivery по `event_id`/`bid_id`; cursor строить по монотонной Auction version, а не по offset ClickHouse.
- Читать Redpanda напрямую средствами ClickHouse Kafka engine и MaterializedView, без отдельного consumer-сервиса.
- Быть eventually consistent и не участвовать в принятии доменных решений.
- Поддерживать переигрывание проекций из retained-событий.
- Отдавать Grafana агрегаты, а Federation interface — историю цены и ставок; текущая цена всегда приходит из Auction.
- Владеть read-only Federation schema и resolver service над ClickHouse; Cosmo Router не обращается к базе напрямую.

- Поставлять собираемый bootstrap binary и собственные multi-stage Dockerfile, Helm chart, ServiceMonitor, PrometheusRule, Grafana dashboard в `ops/`; platform chart не хранит project-specific manifests.

## Последствия

- Выбор брокера ограничен совместимостью с ClickHouse; Redpanda предоставляет Kafka API.
- График может отставать на несколько секунд. Для аналитики это приемлемо, для текущей цены — нет.
- Горячий путь ставки не зависит от ClickHouse.
- В kind появляется отдельный pod ClickHouse.
- Cassandra исключена из кандидатов.
- В перспективе продуктовая аналитика PostHog может использовать тот же класс хранилища, не смешиваясь с операционными данными.
